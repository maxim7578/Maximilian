# Fixes in milestone-7

These are the source changes in the `milestone-7` folder.
A QNX build is still required before a head unit can run them. The daemon and the iDrive app
need to be this build together: the menu asks the running daemon with a ping, and an older
plugin still tries to bind the control port itself.

The MINI 8.8 screen profile and the Bluetooth audio route are kept.
Any `1180x480` panel becomes `1280x480` with DPI 152 and 40 px side insets. Bluetooth audio
uses connection `0xc7` on every car, including Supra. `NBT_BT_CONN=0` falls back to the focus
request. Also unchanged: the timed Bluetooth re-register, the strike-and-hold for a link that
never speaks Android Auto, the `12 34 56 78` BMW-app startup check, CarPlay geometry restore,
the USB log, and the "start with the car" boot-loop guard.

## What changed

1. **A second phone connection no longer replaces the live session.** While a session is up, a new TCP connection is closed. If a session is replaced on purpose, video, audio, and the microphone are torn down first. The listener still prefers the access-point address (`172.16.224.1`, or `NBT_AP_IP`) and refuses a client that is not on that subnet.

2. **Turning touch forwarding off no longer stops the knob, the microphone, or screen handoff.** The wake pipe is always created. Touch events stay off when `NBT_TOUCH_FWD=0`. Input binding on channels 3, 5, and 7 is still accepted, because the phone waits for that answer before it will use the channel.

3. **A fast microphone or screen-focus change is no longer dropped.** Those requests used to share one slot. The main loop could read a value and store zero in the same moment a newer request arrived. They now sit in a short queue.

4. **The BMW-app scan no longer runs for the whole Bluetooth session.** Only the first message of a new link is inspected, and the `DEADBEEF` / `13371337` magic is recognised only at payload offset 8. A later Android Auto frame that happens to contain those bytes is left alone. The four-byte `12 34 56 78` startup magic is still treated as the BMW app.

5. **On/off settings are read the same way.** `0`, `off`, `no`, and `false` are off. `1`, `on`, `yes`, and `true` are on. An unset, empty, or unrecognised word keeps that setting's default. A variable that is merely present does not turn a setting on. This covers wireless mode, the knob, Bluetooth audio, touch forwarding, hide-when-idle, gear and park-assist actions, the packet filter, guidance-over-Bluetooth, the control port, the microphone, reverse focus, BACK-hold focus, Bluetooth refocus, and knob invert.

6. **The menu status file is no longer emptied before it is rewritten.** `/dev/shmem/nbt-aad-state` is one fixed-width line (`idle`, `connecting`, or `connected`, then the pid, then the overlay value). The new line is written first, and the file is shortened after that. Overlay `2` (BACK held) and `3` (a menu key just went to the phone) still fit. The iDrive app checks that the daemon is running by sending `ping` and waiting for `pong`. It no longer binds UDP 52790, which could steal the port from the daemon.

7. **A split message is delivered only when it is complete.** If decryption fails, that channel's partial message is dropped. A LAST fragment is delivered only when the bytes on the wire match the size the phone announced on the FIRST fragment.

8. **The CMake file matches the Makefile.** It lists the same sources, links `a2i_client`, `socket`, `ssl`, `crypto`, and `screen`, and does not pass `-fPIC`. The real head-unit build is still the Makefile (`qcc`, `-std=gnu++0x`).

9. **The older and newer iDrive controllers no longer share one button-state array.** A press on the older CCS controller (C20) is stored separately from the CCS35up hard keys (C47/C4F), so a press on one no longer hides a press on the other.

10. **A Bluetooth close with no accepted Wi-Fi start is a failed handshake.** The phone is treated as joining Wi-Fi only after it accepts the start (status field 4 is 0, or field 3 is 0 when field 4 is absent). Closing right after the access-point details, or sitting for 45 seconds with no accept, is a failure. On that failure the daemon drops and re-registers the Android Auto Bluetooth service. The existing timed re-register is still there for a phone that is connected over Bluetooth and never opens the link.

11. **One tap on the screen reaches the phone as one tap.** The touch forwarder keeps the record sequence of each message. A duplicated message is skipped. A repeated "down" with no message lost in between is sent on as a move. A finger the forwarder has already released (it went quiet for `NBT_TOUCH_IDLE_MS`, or it was missing from a message) is ignored while the head unit still reports it, until the hardware sends "up" or a new "down". A move after a message was actually lost can still start a tap, because that touch's "down" may have been in the lost message.

12. **Only the handshake may be sent unencrypted.** A frame without the encryption flag is accepted only on control channel 0, and there only for VersionRequest/Response, SSL handshake and AuthComplete (ids 1-4) before this session's TLS handshake has finished, and for PingRequest/Response (ids 11/12) at any time, since pings travel in the clear. Before, any plaintext frame went through the normal dispatcher, so a host that reached port 5277 could skip TLS and send video, sensor, microphone or ByeBye messages. Log: `Dropping unencrypted frame on channel ...`, `Dropping unencrypted message 0x.... on channel 0`. (`src/rx_guard.hpp`, `src/aa_session.cpp`)

13. **Protobuf lengths are checked without overflow.** A length field is checked as `len <= n - pos`, never `pos + len <= n`. On the head unit (32-bit `size_t`) a length near 4 GiB in a session message made `pbFirstVarint` jump back and loop forever; over Bluetooth a 64-bit length made `findVarintField` loop and `dumpProto` read past the buffer and crash the daemon. (`src/rx_guard.hpp`, `src/wireless_setup.cpp`)

14. **Split messages are capped over all channels.** Besides 8 MiB per channel, all partial messages together are capped at 16 MiB. Over the total, all partial messages are dropped, since the bytes may sit on channels whose LAST never came. Before, FIRST/MIDDLE fragments without a LAST on many channels could queue up to 2 GiB. A MIDDLE fragment with no FIRST is dropped as well: before, it started a new buffer and a later LAST delivered a message without its start. (`src/rx_guard.hpp`, `src/aa_session.cpp`)

Host test for 12-14: `tests/test_rx_guard.cpp` (`make -C tests run-test_rx_guard`).

15. **The packet filter stays on.** Instead of `pfctl -d` (the whole filter off on every interface until the next reboot), the daemon reads the car's filter rules (`pfctl -sr`), puts `pass in quick proto tcp from any to <address> port 5277 keep state` for 172.16.224.1, 172.16.222.1 and the addresses `uap0` / `wfd0` really have (or only `NBT_AP_IP`) in front of them, and loads them as filter rules only (`pfctl -R -f`), so NAT and tables stay as they are. It checks with `pfctl -sr` that the rule is there, and does it again when the access point comes back. If loading fails, or the phone takes the Wi-Fi details and never connects on every Wi-Fi it is offered (two tries each: with `NBT_ALT_WIFI=BOTH` the hotspot and the Wi-Fi Direct group), it falls back to `pfctl -d` for that run. `NBT_PF=off` is the old behaviour, `NBT_PF=keep` (or `NBT_KEEP_PF=1`) leaves the filter alone. With `NBT_WIRELESS=0` (the outbound scanner) it stays `pfctl -d`. Not car-verified: other traffic of the daemon (cluster SOME/IP, touch UDP) ran with the filter off until now; if something stops working, `NBT_PF=off` brings the old state back. Log: `[PF] ...`. (`src/pf_rules.hpp`, `src/main.cpp`; host test `tests/test_pf_rules.cpp`)

16. **The car microphone needs the Bluetooth step.** TLS does not check the phone's certificate, so anything that reached TCP 5277 could run a session and open the car microphone. Now the microphone is only started and forwarded for a wireless session whose phone did the Bluetooth step (accepted the Wi-Fi start, or still has its Android Auto Bluetooth link open) up to 120 s before the session started or while it runs, or for a USB session. The check runs when the phone opens the mic and for every captured chunk. A host that only knows the Wi-Fi passphrase, or sits on the car's Ethernet, gets no audio. `NBT_MIC_REQUIRE_BT=0` restores the old behaviour; `NBT_WIRELESS=0` (outbound scanner, no Bluetooth step) is unchanged. Log: `[Mic] car microphone for this session: allowed|not yet (...)` at the start, `[Mic] phone asked for the microphone: REFUSED (...)` when it is refused. Known limit: a phone that reconnects over TCP more than 120 s after its last Bluetooth step, without a new one, gets no microphone in that session. A host that connects in the same 120 s as the real phone could still take the session. (`src/mic_guard.hpp`, `src/main.cpp`; host test `tests/test_mic_guard.cpp`)

17. **Only phones on the Android Auto Wi-Fi may connect.** When `uap0` / `wfd0` had no address yet at start, the listener bound every interface and the accept filter fell back to "same network as the address the connection arrived on", which let any host on the head unit's Ethernet (OBD cable) open a session. With `NBT_WIRELESS=0` there was no filter at all. Now, in every mode, the phone has to be on 172.16.224.0/24 or 172.16.222.0/24 or on a network read from `NBT_AP_IF` / `NBT_WFD_IF` (default `uap0` / `wfd0`) or set by `NBT_AP_IP` / `NBT_WFD_IP`; the interfaces are read again, at most every 5 s, whenever a connection is refused. Loopback is refused. `NBT_ACCEPT_ANY=1` lets anyone in. Log: `[TcpServer] refusing ...: not on an Android Auto network`. (`src/alt_wifi.hpp` `aaPeerAllowed`, `src/tcp_server.cpp`; host test `tests/test_accept_filter.cpp`)

18. **The Wi-Fi Direct passphrase is not in the log.** It was printed in clear text (decoded from `WFDPass.conf`) to the RAM log or the USB stick, so anyone with the log could join the car's Wi-Fi. It now shows as `<hidden, N chars; ...>`; `NBT_LOG_WFD_PASS=1` prints it for typing it on a phone by hand. The daemon's log files are created `0600` instead of `0666` (no effect on a FAT stick). (`src/log_secret.hpp`, `src/main.cpp`, `src/alt_wifi.hpp`, `src/usb_log.hpp`; host test `tests/test_log_secret.cpp`)

19. **No touch from the Android Auto Wi-Fi.** The touch forwarder (UDP 30567, all interfaces) took the first sender of a touch PDU as the touch controller, connected to it and saved it in `/var/opt/aa/touch-peer`. A host on the Android Auto Wi-Fi could tap on the phone while Android Auto was on screen and take the controller's place for good. PDUs from 172.16.224.0/24, 172.16.222.0/24 and the networks read from `uap0` / `wfd0` (re-read every 60 s) are now dropped, never learned, and a saved peer on those networks is ignored. The real controller sits on the vehicle network (160.48.199.115 on the cars seen). Log: `[TouchFwd] dropping a PDU from ...`. A host on the vehicle Ethernet is not covered. (`src/local_trust.hpp`, `src/touch_probe.cpp`; host test `tests/test_local_trust.cpp`)

20. **Force Stop only signals nbt-aad.** The iDrive app sent SIGTERM / SIGKILL to the pid in `/dev/shmem/nbt-aad-state`, which the daemon created `0666`. The file is now `0644` (only the daemon writes it), and the app neither signals a pid nor treats it as the running daemon when `/proc/<pid>/exefile` shows another program. An unreadable `exefile` keeps the old behaviour, so Force Stop still works there. (`src/local_trust.hpp`, `rhmiapp/nbt_aad_app.cpp`, `src/main.cpp`)

21. **Android Auto's driving restrictions are on.** The daemon always told the phone DRIVING_STATUS 0 (unrestricted), so the keyboard, long lists and settings stayed usable while driving. It has no vehicle speed, so the default is now 27 = moving (no video, no keyboard, no settings, limited message length; voice input stays allowed). `NBT_DRIVING_STATUS=0` restores the old behaviour, `31` sets every restriction. Log: `Sensor DRIVING_STATUS event (status=27: ...)`. (`src/driving_status.hpp`, `src/aa_session.cpp`; host test `tests/test_driving_status.cpp`)

## Checked here

On a Mac, these host tests passed: companion-app detection (`test_bcl_detect`), both iDrive controller replays (`test_ccs_decoder`, `test_ccs_push`), the car-config / guidance-sink test (`test_car_config`), and the touch parser and forwarder (`test_touch_frame`, `test_touch`, including messages split across datagrams). The changed daemon sources also pass a host syntax check. They have not been built with the QNX compiler and have not been run in a car.
